# Подключение локального анализатора

По умолчанию `backend.cashwatch_adapter:analyze_video` вызывает локальную
экспериментальную модель `ml/weights/hard_negative_detector.pt`: поиск фрагментов
и 16 предполагаемых типов действий после дообучения на сложных отрицательных примерах.
Параметры: [hard_negative_config.json](../ml/weights/hard_negative_config.json).
Прежние `reviewed_detector.pt`, бинарные `detector.pt` и `temporal_candidate.pt`
сохранены отдельно для исторических сравнений. Учебные сценарии frontend не
используются сервером для выдачи результатов анализа.

Для смены checkpoint задайте `CASHWATCH_CHECKPOINT=/абсолютный/путь/model.pt`.
Параметр `CASHWATCH_DEVICE` принимает поддерживаемое PyTorch устройство; `auto`
выбирает CUDA при наличии, иначе CPU. Mac проверяется на CPU. Старый Windows/CUDA
lockfile в `ml/` — описание исходного окружения; для приложения используйте корневые
`requirements.txt` и `requirements-ml.txt`.

## Интерфейс Python

Установите модуль команды и его зависимости в то же окружение, что и сервер.
Модуль должен импортироваться обычным Python, например `team_model.pipeline`.
В нём нужна синхронная функция уровня модуля:

```python
def analyze_video(video_path: pathlib.Path) -> dict:
    # Запустить реальный локальный анализ и вернуть описанный ниже результат.
    ...
```

Вместо dict разрешён `backend.schemas.AnalysisResult`. Загруженный MOV доступен
по абсолютному локальному пути. Функция должна завершиться либо выбросить исключение;
ошибка никогда не должна возвращать `no_violation`. Асинхронные функции и функции,
которые возвращают только текст LLM, нужно обернуть синхронным адаптером команды.

```sh
export ANALYZER_CALLABLE="team_model.pipeline:analyze_video"
uvicorn backend.main:create_app --factory
```

Для отключения встроенного детектора задайте явно пустой `ANALYZER_CALLABLE`.
Если локальные веса/зависимости недоступны, API возвращает HTTP 503. Неверный результат, ошибка импорта
или исключение в модуле дают `failed`. Имя модуля настраивает только оператор
через окружение: пользователь API не может выбирать выполняемый код.

Модуль импортируется в отдельном процессе на каждое видео. Общий бюджет 270 секунд
начинается до разбора multipart и включает загрузку, проверку, очередь и модель;
настройка ограничена 290 секундами. Процесс может быть принудительно
остановлен. Не запускайте неуправляемые отдельные демоны и не храните нужные данные
только в памяти процесса. Если загрузка весов слишком долгая, согласуйте отдельный
локальный модельный сервис и адаптер с ограниченным временем ответа.

## Результат

Без найденных событий:

```json
{"verdict": "no_violation", "violations": []}
```

При найденном событии (строки в угловых скобках нужно заменить реальными данными):

```json
{
  "verdict": "violation",
  "violations": [{
    "type": "<тип наблюдаемого события>",
    "timecode_sec": 44.2,
    "description": "<что видно и почему требуется проверка>",
    "evidence_frames": [{
      "timestamp_sec": 44.2,
      "image_base64": "<base64 настоящего JPEG без data:-префикса>"
    }],
    "rule_source": {
      "document": "<название проверенного нормативного документа>",
      "section": "<пункт или раздел, если известен>",
      "url": "<ссылка на реальный источник, если есть>"
    }
  }]
}
```

Для известного основания `rule_source.document` обязателен и не может быть пустым.
`status=provided` добавляется по умолчанию; `section` и `url` можно опустить.
Не придумывайте нормативные источники. Схема контролирует наличие источника,
но не подтверждает его юридическую точность — это задача команды.

В `ml/cashwatch/rules.json` 16 типов действий сопоставлены с проверенными
17.10.2026 текущими официальными текстами НБРК №231, №14 и АРРФР №53. У восьми типов есть
условно применимое публичное основание. У шести нужны внутренние правила банка,
ещё у двух не установлен достаточный контекст. Для них, а также для старого
бинарного checkpoint и неизвестного типа, передаётся:

```json
{"status": "unmapped", "document": null, "reason": "Тип действия и применимое правило не определены"}
```

Это значение используется в поле `rule_source`. Отсутствующее поле, пустой документ,
пустая причина или выдуманный `document` при статусе `unmapped` отклоняются. Интерфейс
показывает конкретную причину. Контекстные `related_rule_ids` не превращаются в прямое
основание. Наличие реального документа не подтверждает его применимость к видео;
проверяющий должен установить условия, перечисленные в каталоге.
Поля со значением `null` в HTTP-ответе могут опускаться; статус `unmapped` и причина
всегда сохраняются.

Семантический обработчик дополнительно возвращает `type_id`, `type_confidence`,
`description_source="class_template"` и `rule_context` с `applicability_required`,
`limitations`, `source_status`. `type_confidence` лежит в 0–1, но не калиброван:
это оценка класса, а не вероятность нарушения или измеренная точность.
Описание формируется по предполагаемому классу с явной оговоркой о гипотезе.
Человеческие H/J-заметки используются как целевые метки обучения, не как признаки
или готовый текст ответа для загруженного видео. Для произвольного внешнего
обработчика дополнительные поля необязательны.

От 1 до 3 JPEG на событие, до 2 МиБ и 16 мегапикселей каждый. До 100 событий и
24 МиБ полного JSON. Времена — конечные неотрицательные секунды от начала видео.
`violation` допустим только при непустом списке событий. Схема: `backend/schemas.py`.

## Проверка интеграции

1. Загрузить корректный `.mov` через `POST /api/v1/analyze`, multipart-поле `file`,
   заголовок `X-API-Key`; получить HTTP 202 и `job_id`.
2. Опросить `GET /api/v1/jobs/{job_id}` с тем же ключом до `done` или `failed`.
3. Проверить реальный случай с событием, случай без события и ошибку модели.
4. Отключить интернет после установки зависимостей и весов и повторить анализ.

`/health.analyzer_configured` подтверждает настройку и наличие корневого модуля,
а не загрузку весов, наличие функции или качество распознавания. Живой результат
проверяется только полным сценарием. Для интерфейса используется тот же обработчик,
но маршруты `/app/api/v1/...` требуют пользовательскую сессию вместо ключа жюри.
Текущие веса проверены 18.10.2026 на Windows/Python 3.12/CUDA: все 42 файла
прошли новый HTTP-цикл, схемы ответов и JPEG валидны, ошибки обработки отсутствуют.
Полное время — 298,625 с, в среднем 7,097 с на файл (6,016–13,125 с).
Источник: [hard_negative_report.json](../ml/weights/hard_negative_report.json).
Проверки изолированного WSL и публичного HTTPS от 17.10.2026 относятся
к прежним весам `reviewed_detector.pt`:
[исторический технический отчёт](../ml/weights/reviewed_runtime_checks.json).
Эти результаты не подтверждают указанные режимы для новых весов.

Весь анализ должен выполняться локально. Не отправляйте видео, кадры или их
описания облачным AI API. Запрещено подменять анализ фиксированным вердиктом.

## Границы подтверждённого качества

Объединённый набор содержит 40 уникальных видео, 21 положительную и 19 отрицательных
меток, 22 точечных события и 16 типов действий. H/J подтверждены пользователем;
часть исходных бинарных меток и таймкодов сохраняется как слабая разметка.
Большинство типов представлены одним примером. Для них нет проверки обобщения.
Диагностический holdout не доказывает независимое качество: источники связанных
съёмок и пересечение с прежним обучением пока не установлены. Правильный JSON,
декодируемые JPEG, успешный HTTP-цикл и скорость не подтверждают точность модели.

Текущий `hard_negative_detector.pt` дообучает бинарную временную голову
`reviewed_detector.pt`; энкодер, нормализация и голова типов сохранены.
Веса выбраны по тому же обучающему набору; порог 0,5 и постобработка неизменны.
В HTTP-проверке 18.10.2026 на 40 уникальных видео: TP=21, FP=0, FN=0, TN=19,
accuracy и video F1 = 100%. Полностью совпали итог, все события и время ±5 с
без лишних сигналов в 33/40 видео (82,5%).

Полный детектор → таймкод → тип при допуске ±5 с: TP=20, FP=7, FN=2;
precision 74,1%, recall 90,9%, F1 81,6%. Есть 6 лишних сигналов, 1 неверный тип
и 1 пропуск. По времени совпало 21/22 событий; средняя ошибка 0,64 с относится
только к этим совпадениям. Сдвиг 11,5 с на Х-13 (47 → 58,5 с) в среднюю
не включён. Все 42 исходных файла обработаны, точные копии исключены из
основных метрик. Все видео участвовали в обучении и выборе весов;
независимая оценка на новых съёмках отсутствует. Подробности:
[отчёт текущих весов](../ml/weights/hard_negative_report.json),
[PDF по всем видео и событиям](reports/forte-vision-ml-audit-2026-10-18.pdf).

История: первый диагностический запуск 28/6/6 дал typed F1=0 на dev и test;
предыдущий полный fit `reviewed_detector.pt` на всех 40 обучающих видео имел
video F1=0,84 и event/type F1=0,667. Эти показатели относятся к прежним весам:
[исторический reviewed-отчёт](../ml/weights/reviewed_report.json),
[исторический dev/test](../ml/weights/reviewed_diagnostic_report.json).

Замеры прежних бинарных checkpoint не относятся к новому семантическому checkpoint.
Для актуального замера фиксируют SHA-256 весов, платформу, выбранные параметры
и полное время POST → polling → конечный JSON. Технические отчёты не должны
содержать кадры, ключи или тексты сцен. Запрет исходящих Python socket-соединений
проверяется отдельно от изоляции сети на уровне ОС и автономности всего браузерного
приложения. Публичный URL проверяется отдельно после запуска на этом ПК.
